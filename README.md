# Small Fortune

**Your money, translated.**

A currency converter that answers the question you were actually asking. You convert
$20 into Vietnamese dong and get back not just `₫525,562` but what that is: thirteen
bowls of phở, a week of motorbike taxis, a hundred glasses of bia hơi. Turn it around
and $20 of dong in Zurich is most of a coffee.

The number is the boring half. The asymmetry of purchasing power is the product.

## Two different coverage numbers

These are deliberately not the same, and the UI is honest about the gap.

| | Count | Cost to extend |
|---|---|---|
| **Currencies you can convert** | **158** — every live fiat currency the rate provider quotes | Free; regenerated by script |
| **Countries priced in real things** | **131** — 93 sourced, 38 marked `estimated` | Hand-curated; the expensive part |

Converting into an unpriced currency degrades gracefully: you get the rate, plus an
honest "we haven't priced this country yet" instead of a fabricated basket. The picker
marks priced countries with a dot and groups them first.

## How it works

1. All converter state lives in the URL: `/?amount=20&from=USD&to=VND`. Every result
   is a shareable link and the back button does what you expect.
2. The server fetches a USD-based rate table (cached for an hour), derives the
   cross-rate, and picks the destination country's price basket.
3. The client does the arithmetic. Typing a new amount recalculates instantly with no
   round trip; only changing a currency goes back to the server, because that needs a
   new rate and a new basket.
4. The selection algorithm chooses which items to show — favouring counts a person
   would actually say out loud, and spreading them across food, drink, transport,
   housing, goods and leisure so the list reads like a day rather than a menu.


```bash
npm run check        # typecheck + lint + tests — the full gate
npm run test         # node --test, no test framework to install
```

> **Do not run `npm audit fix --force` here.** `npm audit` reports a high-severity

> proposes is `next@9.3.3` — a seven-major-version downgrade that silently rewrites

### What the tests cover

Tests run on Node's built-in runner against `.ts` files directly — no Jest, no Vitest,
no transform step.

`src/lib/logic.test.ts` covers the two places with real decision-making: tolerant
amount parsing (people paste `1.234,56`, `$1,999.99`, `₫ 45 000`) and the line
selection algorithm. It also pins the money formatting, including that a rate of
26,278.14 doesn't render as "26,000" and that `₫525,563` isn't grouped as `525.563`.

`src/data/baskets.test.ts` validates every curated basket — over 1,100 assertions.
Beyond structure (known currency, unique ids, positive prices, five of six categories,
a price ladder spanning at least 50×) it checks two things worth calling out:

- **`dailyWage` plausibility** — a day's pay must buy several of the cheapest item but
  not the dearest. A misplaced zero in a wage figure would otherwise silently corrupt
  the most sensitive string in the product.
- **Tone** — the banned words (*cheap*, *bargain*, *steal*, *exotic*) and exclamation
  marks are asserted against every label and note. The product's main failure mode is
  tonal, so it gets a test rather than a style note.

## Architecture

```
URL searchParams ──► page.tsx (Server Component)
                       │
                       ├─ getRateTable()      cached fetch, 1h revalidate
                       ├─ crossRate()         USD-based derivation
                       └─ getBasket()         static curated data
                       │
                       ▼
                    Converter (Client)
                       │  amount changes → local arithmetic, instant
                       │  currency changes → router.replace → server
                       ▼
                     Receipt
```

### Why state lives in the URL

Next's own guidance is to read `searchParams` in a Server Component when the data
fetch depends on them. It also gets us shareable results, working history, and no
rate data on the client beyond the single cross-rate in play.

### Why the client does the math

A round trip per keystroke would be both slow and rude to the rate provider. The
server hands down one number (`rate`) and one basket; the client multiplies. The URL
is then re-synced on a 450 ms debounce with `router.replace`, so history isn't
flooded with an entry per digit.

### Why `use cache` is off

Next 16's Cache Components (`use cache` / `cacheLife`) are stable APIs but gated
behind `cacheComponents: true`, and their default storage is **in-memory and
per-instance**. On serverless that means constant misses against a rate-limited
provider. The `fetch` Data Cache used in `lib/rates.ts` persists across instances and
deployments instead. This is a deliberate choice, documented in `next.config.ts`, and
worth revisiting when Cache Components become the default.

### Bundle discipline

`lib/basket.ts` (lookup, imports every country's data) is kept separate from
`lib/basket-select.ts` (pure scoring, imports only types). The client imports only the
latter, so the browser receives the one basket being viewed rather than all of them.

## Exchange rates

**Primary:** [`open.er-api.com`](https://www.exchangerate-api.com/docs/free) — no key,
166 currencies, HTTPS, daily refresh.
**Fallback:** [Fawaz Ahmed's currency-api](https://github.com/fawazahmed0/exchange-api)
on jsDelivr, with the Cloudflare Pages mirror as a second attempt.

Attribution to ExchangeRate-API is required by their terms and appears in the footer.

We fetch **one USD-based table and derive every cross-rate by division**
(`EUR→JPY = rates.JPY / rates.EUR`). One cached document covers the entire pair
matrix, which keeps us to roughly 24 upstream calls a day regardless of traffic.

### Providers evaluated and rejected

- **Frankfurter** — well maintained, but serves ECB reference rates only: **30
  currencies**. Worse, requesting unsupported codes returns HTTP 200 with those codes
  *silently dropped* from the response. That's a latent runtime bug, not just a
  coverage gap.
- **exchangerate.host** — no longer the free, keyless option it's remembered as; now
  100 requests/month behind a key.
- **Fixer / Open Exchange Rates / currencyapi** — all workable, but each locks the
  base currency or forbids commercial use on the free tier.

The upgrade path from the primary is a URL swap to the keyed endpoint on the same
provider with the same response shape — no rewrite when the free tier runs out.

## The price data — and why it's curated

The baskets in `src/data/baskets/` are **hand-built**, not fetched. This was the
central research question of the project and the answer was clear.

**Every cost-of-living API sells the same generic basket in every country** — "Meal,
Inexpensive Restaurant", "Cheese, imported (1kg)" — because cross-country
comparability is the entire point of their schema. That is precisely the property this
product has to throw away. The feature works *because* the items are specifically
Vietnamese, or specifically Norwegian. Imported cheese is noise in Hanoi.

### On Numbeo

Not used, at any tier. Their terms prohibit automated collection outright; the free
tier explicitly covers personal blogs, not public products; and even a paid licence
(from $260/month) forbids redistributing the data through a public-facing feed.

**The trap worth naming:** the widely-mirrored Kaggle "global cost of living" datasets
carry a **CC0 Public Domain** badge but are Numbeo scrapes relabelled by uploaders who
had no standing to relicense them. The badge is not clearance. They're also years
stale. This is the most common mistake projects in this space make, precisely because
the licence looks like permission.

### Sources actually used

| `source` | Count | Licence | Role |
|---|---|---|---|
| `local-survey` | 547 | — | The local items. Menus, listings, reporting. |
| `operator-published` | 141 | Published | Fares and tickets read off the operator's page |
| `economist-bmi` | 32 | CC BY 4.0 | [Big Mac Index](https://github.com/TheEconomist/big-mac-data) — one comparable anchor per country |
| `wfp-hdx` | 0 | CC BY 3.0 IGO | [WFP food prices](https://data.humdata.org/dataset/global-wfp-food-prices) — declared and available, not yet used |

Every item records its `source`, which makes refreshes tractable: the CC-BY rows can
be updated mechanically from their feeds, and only the local rows need a human.

WFP is listed because it is the one genuinely open, item-level, redistributable price
dataset that exists — worth reaching for when adding staple-goods rows in the
countries it covers. No current item draws on it, and the table says so rather than
implying broader sourcing than the data actually has.

### What's genuinely not available

Item-level prices by country simply don't exist in open data. World Bank ICP publishes
48 COICOP expenditure headings and no item granularity — it *collects* item prices
under confidentiality with national statistics offices and publishes only aggregated
PPPs. Eurostat HICP is ~500 sub-*indices* (change over time), not price levels. That
constraint is why curation is the answer here rather than the fallback.

## Design

**Neoclassical ledger.** Alabaster ground, olive and oxblood, classical letterforms.
Old-money restraint: two accents and only two, hairline rules, generous letterspacing,
and no ornament that isn't structural.

- **Type:** Cormorant Garamond carries the classical register — high contrast, small
  apertures, a true italic. Jost is the counterweight: a geometric sans whose
  letterspaced capitals read like an inscription rather than UI chrome. Every label in
  the product uses that inscribed voice; classical inscriptions have no lowercase and
  neither do these.
- **Colour:** `--color-olive` for affirmative counts, `--color-oxblood` for the
  emotional beats and warnings. In dark mode oxblood shifts toward a Pompeian brick
  rather than being merely lightened — a lightened wine turns pink, which is entirely
  the wrong register.
- **Ornament:** one letterpress double rule (two hairlines with air between) separates
  sections without drawing a box, and a single short meander marks the head of the
  result. The meander is a square-wave key, not the interlocking classical form: at
  9px the true form turns to mud, and it runs 5rem rather than full width, because
  across 700px a repeating motif reads as noise.

### What the redesign fixed

The first version dressed the result as a tilted paper receipt with stacked edges and
a drop shadow. It was reaching for tactility and instead read as misalignment — in a
layout this spare, a deliberate 0.7° rotation is indistinguishable from a mistake. The
result is now flush to the grid.

**The question is the headline.** There is no hero copy above the converter, because
*"What does $20 USD buy in Vietnam?"* explains the product more directly than any
strapline could — and a strapline would only push the answer below the fold. The
interactive sentence is the first thing on the page; the figure and the list follow
immediately under a hairline. A visually-hidden `<h1>` carries a plain-language title
for screen readers and search.

The old headline — *"Money is just a number until you spend it."* — now closes the
footer instead, where it reads as a parting thought rather than a gate in front of the
tool.

The layout is a **single vertical column** at `max-w-3xl` — question first, answer
beneath — rather than the side-by-side split it started as. Two columns of unequal
height left a dead gutter and made the page read as lopsided; stacking removes the
problem instead of managing it, and the narrower measure suits the classical setting.

Emoji are kept, deliberately. They sit oddly against the high-contrast serif on paper,
but they do real work: the flag identifies a currency faster than its code, and the
item glyphs let you scan a result list without reading it. The compromise is scale —
flags are set at `0.62em` against display type so they punctuate rather than shout.

## Editorial rules

These are load-bearing, not decoration. The product's failure modes are tonal.

**Voice:** concrete, warm, level, curious. The facts are astonishing; the narrator
isn't astonished. Specificity *is* the voice — "a glass of bia hơi" does the work that
"insanely cheap!" destroys.

**Never:**

- Exclamation marks about prices.
- The words *cheap*, *bargain*, *steal*, or *exotic* about a country.
- Finance jargon in the UI (PPP, basket of goods, mid-market rate stay backstage).
- Randomised jokes in repeated states. One calm string beats five quirky ones.
- Telling the reader what to feel.

**Symmetry is the ethical architecture.** Zurich gets exactly the treatment Hanoi
gets. When the copy is wry, the wryness lands on the expensive side ("most of a
coffee"), never the inexpensive one. There is deliberately no "your money is 12×
stronger!" score, because that framing turns a country into a discount bin.

**One contextual line, conditionally.** When a converted amount dwarfs local earnings,
the receipt shows a single factual sentence — *"For context: that's about a day's pay
in Vietnam."* No adjectives, no judgement. It's shown only when true and striking; on
every result it would become wallpaper, and then a sermon. `dailyWage` is omitted
entirely for any country where we couldn't defend a figure — absent beats invented.

## Refreshing the data

Three kinds of data age at completely different speeds, and only one of them is a
real maintenance burden.

| Layer | Freshness | Mechanism |
|---|---|---|
| **Exchange rates** | Daily | Automatic. `fetch` with `revalidate: 3600`; nothing to run. |
| **Currency metadata** | Yearly at most | `npm run gen:currencies`. ISO codes barely move. |
| **Local prices** | **Drifts constantly** | Manual — this is the one that needs discipline. |

Purchasing power is exactly the thing that *does* change, so the third row is the
honest weak point of a curated dataset. Two things keep it from rotting silently.

### The drift canary

```bash
npm run check:drift              # report
npm run check:drift -- --write   # also refresh the Big Mac rows
```

Every basket carries exactly one `economist-bmi` row, and the Economist republishes
the Big Mac Index (CC BY 4.0) in local currency roughly twice a year. That gives one
row per country whose true current value is knowable for free — so we can *measure*
drift instead of guessing at it.

It does not prove the other 19 rows moved by the same amount. But a country whose Big
Mac jumped 30% almost certainly has a stale basket, and one whose Big Mac hasn't moved
probably doesn't. That's the difference between re-checking 36 countries blind and
re-checking the three that need it.

**Time direction matters more than gap size.** The index is a point-in-time snapshot.
If a basket was checked *after* the latest snapshot, a gap is the expected result of
forward-rolling an inflationary economy — not evidence of staleness. Only an index
newer than our data can indict us, and the script reports those two cases separately.
Running it today shows all 32 measurable countries as "ahead of the index" (our data
is 2026-07, the snapshot is 2026-01), with Argentina's −13% correctly classified as a
forward-roll rather than an alarm.

`--write` touches **only** the Big Mac rows, and only when the index is genuinely
newer. Everything else is deliberately left for a human: silently inflating
hand-checked prices would make the data look fresh while making it wrong, which is
worse than being visibly old.

Four countries have no canary — **Nigeria, Kenya, Morocco, Ghana** — because the Big
Mac Index doesn't cover them (three of them have no McDonald's at all). Those are
calendar-driven refreshes with no automated signal, which is worth knowing given NGN
and GHS are among the faster-moving currencies here.

### Telling the reader

The receipt always prints the month its prices were checked. Past nine months
(`STALE_AFTER_MONTHS`) it adds a line in the accent colour saying how old that is and
that the prices are a rough shape rather than today's. Age is computed on the server
and passed down, so the client can't disagree with the rendered HTML about "now".

The point is that stale data should *look* stale. A confidently-rendered wrong price
is worse than an openly dated one.

### Cadence

Target a refresh **twice a year** — but not uniformly.

### Refresh priority

| Cadence | Currencies | Why |
|---|---|---|
| **Every 2–3 months** | ARS, ETB | Parts extrapolated forward, or a recent float that rescales the whole basket |
| **Twice a year** | NGN, EGP, TRY, GHS, BRL, ZMW, BWP, UGX, UZS, KGS, TJS, MMK, LAK, RUB, BYN, MDL, RSD | Inflation, administered step changes, or exchange-rate volatility |
| **Annually** | Everything else | Stable enough that annual is honest |

Pegged currencies inherit their anchor's stability and need the least attention:
**NAD** and **LSL/SZL** track the rand, **XOF** and **XAF** track the euro, and the
USD-pegged Caribbean and Gulf currencies move only when the peg does.

### Four currencies that need a different *method*, not just a shorter cycle

Straight inflation-scaling produces wrong answers for these. Each needs its own
procedure, which is why they're called out rather than left to the cadence table.

- **LBP — recompute, don't nudge.** Beirut is largely dollarized: rent, the generator
  subscription and anything imported are quoted in USD and settled in fresh notes.
  Those rows were sourced in dollars and carried across at ~89,500 LBP/USD; only the
  ministry fares and the subsidised bread bundle are natively in pounds. If the pound
  moves, re-derive the dollar rows at the new rate rather than scaling the basket.
- **ETB — re-anchor first, then rescale.** The birr has floated since July 2024 and
  roughly tripled against the dollar. The basket is priced against ~155 ETB/USD; if
  that assumption is off, *every* row is off by the same factor. Fix the anchor before
  touching any individual price.
- **BYN — watch decrees, not CPI.** Belarusian prices are administered, so they move in
  overnight steps rather than drifting. The March 2026 transport decree moved fares 15%
  in a day. A CPI-based adjustment models the wrong process entirely.
- **MMK — pick a reference rate and record it.** Myanmar is priced at the market rate
  (~4,500 MMK/USD), not the official ~2,100. If a future refresh switches reference
  rate, every row moves together. The choice matters more than any individual price.

### Which countries have no drift canary

The Big Mac Index covers 54 countries, so most baskets have no automated staleness
signal — McDonald's doesn't operate in any of the twelve `africa2` countries, exited
Russia in 2022 and Sri Lanka in 2023, and never reached Iraq. Those baskets are
calendar-driven only.

Don't maintain that list by hand — **`npm run check:drift` prints it** under "No canary"
on every run, alongside the countries it *can* measure. The set changes whenever the
Economist republishes.

### Known weak spots

Recorded honestly so the next refresh knows where to look first, rather than
re-verifying 36 countries uniformly.

- **ARS (Buenos Aires) is the weakest data in the repo.** Rent and wage inputs are
  near-current, but the food, drink and transit rows were rolled forward from
  January 2026 anchors using ~14.7% H1 inflation rather than observed directly. The
  `dailyWage` is a further step removed — RIPTE is a *mean* over stable formal
  workers, discounted to an assumed median. Treat that figure as indicative.
- **BRL `dailyWage`** is derived from a national PNAD *mean* with no clean São Paulo
  metro median available. The BR prices themselves are solid (Procon-SP, SPTrans).
- **SEK — a dated figure by design.** The 30-day SL card is priced at 530, which is
  what riders actually pay under the state's 1 Jul–31 Dec 2026 halving. **It reverts
  to ~1,060 in January 2027** — worth a calendar entry, not a guess.
- **MXN `dailyWage`** is formal-sector only; the IMSS median excludes roughly half the
  metro workforce, who earn less.
- **NGN** street-food and danfo rows are triangulated from reported ranges — assume
  ±25%. Rent listings skew formal, so the Mainland one-bed figure reads high.
- **EGP** butagas and cigarette rows are administered prices that move in discrete
  steps and were extrapolated, not confirmed. The five-loaf bread row is deliberately
  the *ration* price, flagged in its `note`; the free-market price is several times it.
- **TRY** anchors (transit tariff, minimum wage, rent) are current and strong; the
  street-food rows are extrapolated from them.
- **KES** — the SGR Nairobi–Mombasa economy fare is the long-standing figure; a more
  recent increase could not be confirmed either way.
- **BOB — a deliberate choice, not an oversight.** Bolivia's dollar-scarcity crisis has
  opened a real gap between the official and street exchange rates. Prices are what a
  resident actually hands over in a shop, unadjusted for that gap, because that is the
  question this product answers. Converting *into* BOB at the official rate will
  therefore overstate what the money buys.
- **SGD** — the COE row (S$105,000) swings 20%+ between bidding rounds and will date
  faster than anything else in the repo. It is kept because it is the number
  Singaporeans actually quote, and because the ladder needs a top anchor.
- **Fuel rows** (VND, IDR, MYR, AUD) move weekly; only Pakistan's is pinned to a dated
  source. **PKR `dailyWage`** is anchored on the Sindh statutory minimum rather than a
  median — the weakest of the twelve APAC wage figures, kept on the same reasoning as
  Indonesia's (a statutory floor that the low-to-mid wage mass genuinely clusters at).
- **Spot-check first on a refresh:** Karachi biryani, the Mumbai auto-rickshaw minimum,
  and the Hanoi one-bed rent (sources spanned ₫3–10m; the midpoint was taken).

### Rents are the highest-leverage rows in the repo

Nearly every basket's weakest figure is its monthly rent, and rent is also the **top
ladder anchor** — so an error there skews which items the selection algorithm picks at
every amount, not just that one line. Several regions had no reachable listings source
(Numbeo is excluded by policy; Expatistan 403s), so those rents are triangulated from
aggregate reporting.

Re-check rents first, everywhere. **Manama and Muscat** are the most likely to be
wrong: the figures found read as expat-package rather than resident pricing and were
marked down deliberately. Tbilisi, Yerevan and Bishkek moved fast post-2022 and are
next. The twelve `europe2` rents are hand-estimated rather than read off an index.

### Estimated baskets, and why the flag exists

Thirty-eight of 131 baskets carry `estimated: true`:

- **Africa (8)** — Angola, DR Congo, Madagascar, Malawi, Liberia, Mauritania, Guinea,
  Burundi
- **Pacific & Asia (9)** — Fiji, Papua New Guinea, Samoa, Vanuatu, Solomon Islands,
  Tonga, French Polynesia, Bhutan, Brunei
- **Caribbean (9)** — Bahamas, Barbados, Belize, Guyana, Suriname, St Lucia (Eastern
  Caribbean), Aruba, Cayman Islands, Bermuda. Wages, some fares and some rents were
  genuinely read off government and operator pages; the food, drink, goods and leisure
  rows are calibrated against those anchors rather than read off menus
- **Latin America (12)** — Chile, Peru, Bolivia, Paraguay, Uruguay, Costa Rica, Panama,
  Guatemala, Dominican Republic, Jamaica, Trinidad & Tobago, Honduras. Minimum and
  average wages were live-fetched and are solid; item prices are survey-level. Uruguay,
  Jamaica and Trinidad are the weakest — their wage anchors are 2020–2024 figures
  extrapolated forward

Their *relative* ladders are sound (a meal really does cost about what it says relative
to rent) but their absolute price levels were derived from verified exchange-rate
anchors plus domain knowledge, not from sourced local prices.

The cause was mundane and worth recording: the research budget is **shared across the
whole session**, and it was exhausted before these agents ran. They said so instead of
passing the work off as verified — *"this is informed estimation rather than a fresh
field survey"* — which is the only reason the flag exists at all.

The flag exists because of a specific failure mode. **A well-written basket reads
identically whether its numbers were researched or inferred.** These eight are
culturally specific, correctly scaled, tonally clean and pass every structural test —
and none of that constitutes verification. Left unmarked, the polish would imply a
confidence the data doesn't have, which is the same mistake as a mislabelled `source`.

The receipt says something different for them:

> Estimated prices for Luanda, 2026-07. We haven't been able to source these locally
> yet — the proportions are right, but treat the amounts as a sketch.

`estimated` is `true` or absent, never `false` — absence is the verified state, and a
test enforces that, because `false` would read as an active claim we don't make.

**These are first in line for a research pass**, and the work is well-defined:
re-anchor each against sourced local prices rather than FX. Papua New Guinea and the
Solomon Islands are the weakest of the set and worth doing first. One non-estimated row
also needs attention: **Guyana's rent** (GYD 180,000) was inferred as a resident figure
because the only listing found was an expat-oriented US$2,500 one. Until then the product
still works — the asymmetry a reader feels is carried by the ladder, not the absolute
scale — but the reader is told which is which.

### Rows waiting on a source that was unreachable

- **African staples** — teff, sembe, posho, roller meal, riz brisé, maize meal — *should*
  be `wfp-hdx`. HDX returned 403 to every request (dataset pages and the CKAN API), as
  did FAO FPMA, so they are currently `local-survey`. Re-source and flip the `source`
  field the moment HDX is reachable; the licence (CC BY 3.0 IGO) already permits it.
- **Transit fares in the Caucasus and Central Asia.** Baku Metro, Tashkent Metro, Tbilisi
  Transport Company and Almaty Metro all 404'd or blocked automated requests, so *no*
  row in that file claims `operator-published`. Upgrading those needs a human with a
  browser. First to fix: Tashkent metro, Baku metro, Almaty Onay, Bishkek bus, Dushanbe
  bus.
- Some South-East Asian rows (Myanmar, Laos, Cambodia food and transport, Nepal transit)
  rest partly on priors because the research budget ran out mid-task. Harden these
  before trusting them.

Two deliberate structural choices in the housing rows: Sydney's top anchor is a
four-week **rental bond**, because Australian rent is quoted weekly and a single week
left the ladder topping out too low; Seoul's is the **wolse deposit**, which is the
number that actually gates Korean housing.

### A note on `source` accuracy

`operator-published` means the figure was read off the operator's own fare or ticket
page — not that it is the kind of thing an operator publishes. Eleven APAC cinema rows
were initially tagged that way while being chain-typical estimates; they are now
`local-survey`, which is what a triangulated figure is. Keep that distinction honest:
the value of per-item provenance is that a future refresh can trust the label and
re-pull only what is mechanically re-pullable.

### Lebanon is a different kind of stale

**LBP needs recomputing, not nudging.** Beirut is largely dollarized: rent, the
generator subscription and anything imported are quoted in dollars and settled in
fresh notes. Those rows were sourced in USD and carried across at ~89,500 LBP/USD.
Only the ministry fares and the subsidised bread bundle are natively in pounds.

So if the pound moves, scaling the LBP basket by inflation is *wrong* — the
dollar-denominated rows have to be re-derived from their USD prices at the new rate.
That makes it structurally unlike the TRY/EGP/NGN case, where the prices really are
local-currency prices that drift.

### Gulf states: why no `dailyWage`

GASTAT, LMRA, Qatar's PSA and Oman's NCSI each report national and non-national pay
*separately*, and the two distributions barely overlap. A blended median describes
nobody. Since this field drives a "that's about a day's pay here" line, the field is
omitted for all six Gulf states. Jordan is the one country in the region whose
published median describes a workforce that is actually mostly counted.

### Middle East weak spots

- **All eight rents** are triangulated from aggregate reporting rather than listings
  portals. **Manama and Muscat are the most likely to be wrong** — the figures found
  read as expat-package rather than resident pricing and were marked down deliberately.
- **Iraq is the weakest basket in the region.** Internal ratios are sound (samoon 250,
  kia leg 1,000, taxi 10,000, masgouf 25,000) but absolute levels are ±30%. The
  generator-ampere row is the single row most worth a local check.
- Iraq and Lebanon carry **no Big Mac row** — Iraq has no McDonald's and Lebanon
  couldn't be confirmed in the current index — so they have no drift canary.

`dailyWage` is deliberately **omitted** for Nigeria, Kenya, Ghana and the UAE. None has
a defensible published median — Kenya's KNBS series is formal-sector only, Nigeria's
NBS publishes no median, Ghana's workforce is largely informal, and the UAE's is too
stratified for any proxy to hold. Since that field drives the most sensitive string in
the product, absent beats invented.

To add a country: append a `Basket` to the matching regional file in
`src/data/baskets/`, matching `currency` and `countryCode` to `src/lib/currencies.ts`.
16–20 items, spread across all six categories, with a wide price ladder — the
selection algorithm needs range to pick good lines at both $2 and $2,000.

## The currency picker

A native `<select>` over 158 options is a wall, so the picker is the ARIA combobox
pattern: a trigger that reads as part of the sentence, and a compact popover with
type-to-filter. Full keyboard support (arrows, Home/End, Enter, Escape, Tab),
`aria-activedescendant` tracking, click-outside dismissal.

Search matches **code, currency name, country, and member-state aliases**, with accent
folding — so `cote` finds Côte d'Ivoire and `curacao` finds Curaçao. The aliases matter
because shared currencies are otherwise unreachable by the name people actually know:

| You type | You get |
|---|---|
| `spain` | 🇪🇺 EUR — European Union · *Spain* |
| `ivory` | 🇸🇳 XOF — West African CFA zone · *Ivory Coast* |
| `panama` | 🇵🇦 PAB — Panama, **and** 🇺🇸 USD — United States · *Panama* |
| `liechten` | 🇨🇭 CHF — Switzerland · *Liechtenstein* |

When a row surfaces via an alias, the alias is shown beside the country — otherwise
typing "Spain" and getting "European Union" reads as a bug rather than a fact.

### Regenerating the currency list

```bash
npm run gen:currencies
```

Reads the provider's live currency set and rewrites `src/lib/currencies.ts`. It is
**merge, not overwrite**: existing rows keep their hand-curated symbol, name and
`decimals`, so deliberate calls (IDR displayed with 0 decimals against ISO's 2) survive
regeneration. Only genuinely new currencies are derived from `Intl`.

Three categories get special handling.

**Accounting units are excluded** — XDR (IMF Special Drawing Rights), CLF (Chile's
inflation-indexed Unidad de Fomento), XTS, XXX and the precious metals. The provider
quotes them, but they are not money anyone spends, so offering them as a destination
is nonsense.

**Retired currencies are excluded.** The provider still returns rates for currencies
that no longer circulate, which makes them look alive in an API response. Converting
into one tells the reader nothing about what money buys there today:

| Code | Why it's gone |
|---|---|
| `HRK` | Croatia adopted the euro on 2023-01-01 |
| `ANG` | Ceased legal tender 2025-07-01, superseded by `XCG` |
| `SLL` | Redenominated to `SLE` in 2022 (1000:1) |
| `ZWL` | Replaced by `ZWG` (the "ZiG") in April 2024 |
| `CNH` | Offshore renminbi — the same currency as `CNY`, not a second one |

A test asserts each is absent *and* that its live successor is present, so a future
regeneration can't quietly resurrect them. A second test asserts no country is listed
with two currencies, which is the symptom a surviving retired code produces — that's
how `CNH`/`SLL`/`ZWL` were caught in the first place.

**Shared currencies** (EUR, XOF, XAF, XCD, XPF, XCG) get a representative flag plus a
member-state alias list, since their code prefix names no country.

`currencies.test.ts` guards the output — including that every flag emoji's regional
indicators actually *spell* its `countryCode`, which is the failure a generator makes
silently and a reader notices immediately.
